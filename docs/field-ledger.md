## C. Findings, ranked

### Wrong (the spec disagrees with the sources)

- **W-1 `power_on.mode` merges two different camera settings.** Spec:416 maps `wake mode M` and
  spec:471 maps `startup set --ai M|none`, both to `set power_on.mode`. In 0.13 these are separate:
  `wake mode` = short `19` "default work mode" (cmds.rs:194-199, cam.rs:769; readback status `0x20`,
  st.rs:63-68; firmware notes "RAM structure, not shown to persist", inv:501), while `startup --ai`
  = byte 0 of the initial-state block `0x3e44`/`0x3e84` (pre.rs:235-275, cam.rs:1006). The option
  sets differ: short `19` takes all 8 modes; the initial state offers only
  static/normal/upper_body/headless/group/none (README:223-226 "close-up, lower body and hand are not
  offered: values not verified"), and in it `static` (0xff) and `null`/none (0xfe) are different
  values (pre.rs:248-253). Fix: two fields (for example `power_on.tracking` = `0x3e44` byte 0 and
  `power_on.default_mode` = short `19`, or drop one after a live test), each with its own readback
  and writable options.
- **W-2 "Daemon remembers" list is wrong for `zone.follow` and the power-on pose.** spec:131,
  spec:308, spec:313 say these are remembered and lost on migration. Both are read from the camera:
  `zone.follow` = query `0x4e44` (cmd.md:55,76, VL; cam.rs:476), the power-on pose = query `0x3884`
  (cmd.md:79, VL; cam.rs:540). 0.13's `state.json` holds only `gimbal` and `exposure_mode`
  (state.rs:99-104), so the migration note in spec:310-313 promises an import that does not exist
  for these two, and LED blink was never saved in 0.13 either (cam.rs:759).
- **W-3 `exposure.mode` is not necessarily daemon-only.** global/face is status `0x07`
  (sb.md:20); manual is V4L2 `auto_exposure`=1, and the firmware has query `0x2402` / `0x2942`
  for the AE mode (inv:51,54; 0.13 used `0x2942` live to check manual mode, cam.rs:1047-1048).
  Only the V4L2 cache can go stale after short `03` (cmd.md:26). Rank: wrong as stated ("cannot
  report"); keep a remembered fallback if `0x2402` needs a running stream (inv:51 "media busy").
- **W-4 `power_on.image` is mis-typed and mis-named, and writing the pose wipes it.** spec:216
  says "same fields as image, read-only". The `0x3e84` block holds AI mode, tracking speed,
  autofocus, AF mode, auto exposure + metering + EV, WB mode + Kelvin, contrast, saturation,
  sharpness, hue (presets.md:57-71, pre.rs:302-338). It has no brightness, backlight, mirror or flip,
  and half of it is not "image". Also, 0.13 writes the pose as `0x3ec4` **plus** a cleared `0x3e44`
  block, which clears these settings (README:225-226, pre.rs:279-287). So `set power_on.pose`
  silently changes the read-only `power_on.image`. Either keep the block (as `startup_with_ai` does,
  pre.rs:289-295) or document the side effect.
- **W-5 `zone.return` cannot be `null`.** spec:203 `return {pan,tilt,zoom}|null`. The camera has no
  "not set" state for it: the leading word of `0x4ec4` is always 0, and a fresh camera answers
  0/0/1.0 (cam.rs:222-227, README:210-212, CHANGELOG 0.12 "#57"). Only `hand.return` has a null
  (leading −1, cmd.md:80).
- **W-6 `tracking.target.box` layout.** spec:197 says `box[x,y,w,h]`. 0.13 documents the four floats
  as left, top, right, bottom (st.rs:244). The inventory says the record layout is "not decoded"
  (inv:157). One of the two is wrong; at most one can be right. Verify before freezing the schema.
- **W-7 `sleep.background` lacks the read-only own-image value.** Status `0x1b` reads 3 after an
  upload (sb.md:35, cap18, VL). 0.13 maps 3 to `null` (st.rs:79-80). By the spec's own rule (spec:160,
  FOV `custom`), the description needs a read-only `custom`/`own_image` option.
- **W-8 Anti-flicker: an option and an interlock are missing.** 0.13 decodes and names status
  `0x03` = 3 as `auto` (st.rs:46-60, test st.rs:304-313); the spec's enum stops at 60hz
  (spec:207). Whether `auto` is writable on the Lite is unclear (sb.md:17 lists only 0–2), so at
  least it is a read-only option. The firmware also refuses anti-flicker writes in manual and
  shutter-priority exposure (inv:52), so the safe `set` order (spec:124-127) must put
  `anti_flicker` before `exposure.mode=manual`.
- **W-9 "Only mirror is known to be reachable from the host" (spec:228-230) is too strong.** The
  AI process registers host-reachable request handlers `0x6904` set mirror, `0x6944` set flip and
  `0x6984` set mirror+flip on receiver 4 (inv:371-373, "works (inferred)"). They are firmware-only
  and untested, so leaving flip out of the Lite's description is still right, but the note should
  name `0x6944` as the candidate to test. Note that `0x6484` also flips the turn direction for
  `gimbal_flip` / `camera_flip` (inv:378), so the mirror-xor-invert correction would need to grow.
- **W-10 spec:249 "`power_on.pose` cannot be cleared on the camera"** conflicts with `0x38c4`
  `AI_OPTION_GIMBAL_RESET_INIT_PRESET` (inv:209, FW "works (inferred)"). Say "no verified way";
  `0x38c4` is the candidate.
- **W-11 spec:305 "measured: zoom and FOV are ignored"**: only FOV has a source (cmd.md:22). No
  primary source records zoom being ignored while asleep. Known asleep facts that the description
  should carry: FOV ignored; `power_on.go` ignored (cmds.rs:360); queries `0x80c2` and `0x3642`
  do not answer, so `audio.volume` and `focus.*` from `0x3642` are unknown while asleep
  (cam.rs:629-634).

- **B-6 / B-7** per-preset and initial-state picture settings (Center offers both, CAP, partly
  decoded).
- **B-2** shutter priority, **B-11** recall speed, **B-12**–**B-16**: firmware-only, fine to defer
  but worth listing in the spec's "Later".

### Questionable (model quality)

- **C-1 `tracking.hand_side` belongs to `hand`.** The model has a `hand` group (area, axes,
  return_after, gimbal, return), and the firmware stores the side in the same hand-tracking option
  set (`0x2004` byte 20, inv:339). 0.13's command is `hand left|right` too.
- **C-2 Duplicates.** (a) `focus.auto` and `focus.mode=continuous` are the same camera bit: status
  `0x0e` is "continuous autofocus on" (sb.md:25), and `0x3442` 1 sets it while 2/3 clear it (cmds.rs:70-73).
  The spec leaves this "open" (spec:240-242), but the 0.13 measurement already answers it; keep one
  field. (b) `audio.pickup` is a quantised view of `audio.volume`: short `1b` sets the volume to
  10/50/100 and status `0x22` is derived from the volume (inv:503, inv:74). Writing one changes the
  other, so the description should say so, or `pickup` should be a preset action.
  (c) `tracking.mode` sub-modes write the framing fields (upper_body/close_up = auto_zoom + size MS/MCU,
  headless/lower_body = `framing.part`; inv:244,246,248, cmds.rs:46-66), so a patch with both needs
  a defined order (mode first) and clients will see `framing.*` change after a mode change.
- **C-3 Names that confuse with Center and with 0.13.** `tracking.style` is what Center labels
  "Tracking speed: Standard / Sport" (cp:42), while `tracking.speed` is the firmware `speed_mode`
  that Center does not show. `style` also mixes a framing variant (headroom) with a gain choice
  (sport). Suggest `tracking.profile` (or `tracking.vertical`) and `tracking.speed`. In focus, 0.13
  `focus mode face|global` becomes `focus.target` and 0.13 `focus af …` becomes `focus.mode`
  (spec:463-465). The same word now means the other thing, which will break users' muscle memory.
- **C-4 `image.backlight_compensation` is probably exposure compensation (guess).** In capture 12
  the only writes in the "compensation" step go to UVC PU selector 1 (backlight compensation)
  (cap12 t=476.38-491.51). If confirmed live, it belongs in `exposure` as `exposure.compensation`.
  Mark it as a guess until verified.
- **C-5 `framing` overlaps `tracking`.** See C-2(c). Grouping is acceptable, but the description
  should say "overwritten by tracking.mode" (0.13 help says so: cli.rs:169).
- **C-6 `zone.views` are not zone settings.** The firmware never reads them for tracking
  (cmd.md:58 "do not change tracking"; README:228-232). They are named poses like presets, so a
  top-level `views` next to `presets` fits the user meaning better. Center calls them
  "non-tracking areas" (cp:90); the spec's name is fine, the group is not.
- **C-7 `gestures.direction_change`** is "dynamic-zoom direction inverted" (inv:320), a sub-option
  of `dynamic_zoom`, not its own gesture. A name like `dynamic_zoom_reverse` would say what it does.
- **C-8 `hand.gimbal` and `camera.led.blink` are Center dialog internals exposed as settings.** Center
  sends them only while a settings dialog is open (cmd.md:27,48; cp:151 "not a user setting").
  Neither has a readback, `hand.gimbal` is not stored by the camera (cmd.md:48), and neither is in the
  spec's remembered list. Both are kept for parity, but they behave like transient holds. Consider
  actions (`hand.hold` / `hand.release`) or mark them `volatile` so a restart does not leave a stale
  daemon value.
- **C-9 `camera` is a grab-bag group.** It holds LED (device indicator) and `frame_rate` (stream
  info). `frame_rate` sits better with `on_air` (stream state), and LED as `led` at top level.
- **C-10 `power_on.wake_zoom` is a wake-from-sleep value by name and firmware** ("zoom factor used
  after waking", inv:497). Under `power_on` it reads as power-on. It has no observed effect at
  either (CHANGELOG:20-22). `sleep.wake_zoom` matches the firmware. The current spot follows 0.13's
  finding that `wake mode` acts at power-on, which is a different command (W-1).
- **C-11 `gimbal.center` is promoted from a hidden, misbehaving command.** 0.11 recorded that it "moved
  the gimbal only toward the left and downwards in tests" (CHANGELOG:90-91) and hid it. Without a
  fix it should stay out of the schema or be marked experimental.
- **C-12 Inconsistent "current pose".** `zone.return_here`, `hand.return_here` and `view.save` use
  the live pose `0x0043` (cam.rs:826-833). `preset.save` without a pose and `power_on.use_current`
  use the remembered pose or stale V4L2 values (cam.rs:1200-1218). In 1.0 the live pose is always
  available, so all of them should use `0x0043` + `0x6804`.
- **C-13 Verification levels to carry into the description** (spec:396-397 "UNTESTED" rule): rows
  10, 13, 14, 16, 17, 29, 30, 31, 46, 50, actions a3, a5, a6, a12, a19, a20, a25 rest on firmware
  reading plus 0.13's own use, not on a replay with an observed effect. `tracking.style=headroom`
  is "not tested" (cmd.md:36).

Guesses, marked as such above: C-4 (EV = backlight compensation), B-9 (mic state from the UAC
interface), and which of the two box layouts in W-6 is right.
